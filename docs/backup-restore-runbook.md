# バックアップ・復旧手順書（ISMSを意識した暫定版）

## 1. 手順書の目的

本手順書は、lab-managerで扱う予約情報、利用料金、請求情報、監査ログなどを障害・誤操作・データ破損から復旧するための基本手順を定めるものです。ISO/IEC 27001への正式準拠を示すものではなく、復旧判断、作業分担、記録、訓練を通じて安全運用に近づけるための暫定手順です。

本番環境での復旧作業は、影響範囲と停止時間を確認し、承認を得たうえで実施してください。接続URL、パスワード、秘密鍵、証明書の実物は、この文書やGitHubに記載しません。

## 2. 現在確認できているシステム構成

- アプリケーション：Next.js
- 本番展開：GitHubの`main`ブランチからVercelへ展開
- ORM：Prisma
- データベース：PostgreSQL（提供事業者は本書作成時点では断定しない）
- 接続設定：`DATABASE_URL`（通常接続）と`DIRECT_URL`（直接接続）を使用
- 電子印画像：`User.sealImage`
- PDF署名証明書：`certificate.p12`
- Vercel環境変数：`AUTH_SECRET`、SMTP設定などの秘密情報を保持

アプリケーションのソースコード、Prismaスキーマ、移行スクリプト、Vercel設定、データベースのバックアップは、それぞれ復旧に必要な構成要素として管理します。

## 4. 復旧目標（暫定）

- 暫定RPO（許容するデータ損失）：24時間
- 暫定RTO（復旧目標時間）：8時間
- 自動バックアップ：1日1回以上を目標とする
- 保存期間：35日以上を目標とする

これらは暫定目標です。DB提供事業者、契約プラン、バックアップ機能、業務上の許容停止時間を確定した後に見直してください。

## 5. DB構造変更・大量更新前のバックアップ

1. 変更内容、対象環境、予定時刻、影響範囲、復旧判断責任者を記録します。
2. 本番DBに対する作業を止める、または同時更新が発生しない時間帯を設定します。
3. 本番DBとは別の安全な保管場所へ、作業直前のバックアップを取得します。
4. バックアップファイルの作成日時、対象DB、実行者、ファイルサイズ、ハッシュ値を記録します。
5. 復旧確認用PostgreSQLへリストアできることを確認してから、構造変更・大量更新を実施します。
6. 変更後にアプリケーションの主要機能と件数を確認し、異常時に戻すバックアップを特定します。

バックアップファイルには個人情報や請求情報が含まれる可能性があります。アクセス権を限定し、暗号化・保管期間・削除時期を組織のルールに従って管理してください。

## 6. `pg_dump`による手動バックアップ例

以下は例です。実際の接続情報は、承認された安全な保管場所から環境変数などで受け取り、コマンドやログへ直接書き込まないでください。

```bash
export PGDATABASE_URL='承認済みの接続情報を安全に設定'
pg_dump "$PGDATABASE_URL" \
  --format=custom \
  --file="./backup/lab-manager-$(date +%Y%m%d-%H%M%S).dump" \
  --no-owner \
  --no-privileges
```

実行後、バックアップファイルが作成されたことを確認し、可能であれば次のようにハッシュ値を記録します。

```bash
shasum -a 256 ./backup/lab-manager-YYYYMMDD-HHMMSS.dump
```

`PGDATABASE_URL`の値、パスワード、秘密鍵、証明書を画面共有・チャット・GitHub・作業記録へ貼り付けないでください。

## 7. 復旧確認用PostgreSQLへの`pg_restore`

本番とは別に用意した復旧確認用PostgreSQLへ、バックアップをリストアします。復旧確認用DBの接続先は本番アプリケーションに設定しないでください。

```bash
export RESTORE_DATABASE_URL='復旧確認用PostgreSQLの接続情報を安全に設定'
createdb "$RESTORE_DATABASE_URL"  # 既存DBを使う場合は実行しない
pg_restore \
  --clean \
  --if-exists \
  --no-owner \
  --no-privileges \
  --dbname="$RESTORE_DATABASE_URL" \
  ./backup/lab-manager-YYYYMMDD-HHMMSS.dump
```

既存の復旧確認用DBを再利用する場合は、対象DBを間違えていないことを二人で確認してから`--clean`を使用してください。復旧後は件数確認SQL、ログイン、予約表示、予約作成・更新・削除、利用料金、請求書、監査ログを確認します。

### 重要な警告

**復旧確認では本番DBへ直接`pg_restore`しないでください。** 本番DBへの復元が必要な場合は、復旧判断責任者の承認、作業前バックアップ、停止・切替計画、確認者の立会いを必須とし、別途作業記録を残してください。

## 8. 復旧後の件数確認SQL

復旧確認用DBへ接続し、次のSQLで主要テーブルの件数を確認します。期待値はバックアップ取得時の記録、または障害発生前の既知の値と比較してください。

```sql
SELECT 'User' AS table_name, COUNT(*) AS row_count FROM "User"
UNION ALL
SELECT 'Equipment', COUNT(*) FROM "Equipment"
UNION ALL
SELECT 'Reservation', COUNT(*) FROM "Reservation"
UNION ALL
SELECT 'Reagent', COUNT(*) FROM "Reagent"
UNION ALL
SELECT 'UsageLog', COUNT(*) FROM "UsageLog"
UNION ALL
SELECT 'Invoice', COUNT(*) FROM "Invoice"
UNION ALL
SELECT 'InvoiceItem', COUNT(*) FROM "InvoiceItem"
UNION ALL
SELECT 'AuditLog', COUNT(*) FROM "AuditLog"
ORDER BY table_name;
```

## 9. Preview環境での動作確認項目

本番切替前に、復旧確認用DBまたは検証用DBを接続したPreview環境で次を確認します。

- ログイン、ログアウト、パスワード関連の既存機能
- 管理者・センター長・一般利用者の権限チェック
- 機器一覧、有料サービス一覧、利用者一覧、監査ログ一覧の表示
- 予約の作成・更新・削除と、重複予約の拒否
- 利用料金記録、請求書、請求書明細の表示
- 電子印画像・PDF署名に必要なファイルや環境変数の設定確認
- 監査ログの記録と、監査ログ記録失敗時に本体操作が継続する設計の確認
- 日本語のエラー案内と、スマートフォン表示を含む主要画面

Previewで使用したデータは本番利用者へ公開せず、個人情報を含む場合はマスキングまたはアクセス制限を行います。

## 10. 本番切替と旧DBへ戻す手順

### 本番切替

1. 復旧判断責任者が切替を承認し、利用者へ必要な停止案内を行います。
2. 本番DBへの更新を停止し、直前バックアップを取得します。
3. 復旧確認用DBで件数・主要機能・権限・監査ログを確認します。
4. 切替対象DBの接続設定を、承認済みの手順でVercel環境変数へ設定します。秘密情報は画面や記録へ転記しません。
5. Vercelの本番展開を行い、ヘルスチェックと主要機能を確認します。
6. 復旧確認者が結果を確認し、切替時刻と判定を記録します。

### 旧DBへ戻す場合

1. 異常の内容、影響、戻す判断、データ損失の可能性を復旧判断責任者が確認します。
2. 現在のDBをバックアップし、旧DBへ戻す対象と時点を明確にします。
3. アプリケーションへの書き込みを停止し、Vercelの接続設定を旧DBへ戻します。
4. 本番DBへ直接復元する必要がある場合は、承認・バックアップ・二者確認の手順を満たしてから実施します。
5. ログイン、予約、料金、請求書、監査ログを確認し、利用者へ復旧状況を案内します。
6. 旧DBへ戻した理由、失われた可能性のある更新、再発防止策を復旧記録へ追記します。

## 12. 復旧訓練

3か月ごとに、少なくとも1回は復旧訓練を実施します。訓練では復旧確認用PostgreSQLへのリストア、件数確認SQL、Preview環境での主要機能確認、役割分担、記録様式、RPO・RTOの実績を確認します。訓練後は結果、所要時間、問題点、手順書の改訂内容を記録してください。
